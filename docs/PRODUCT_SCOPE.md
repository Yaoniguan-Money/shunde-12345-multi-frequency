# PRODUCT_SCOPE.md

## 当前冻结产品方向

这是“顺德 12345 多频工单智能研判”，不是通用 RAG 问答助手。

主闭环：

`Excel/CSV导入 → 工单理解 → 实体归一 → 同事件识别 → 多频事件组 → 可核查依据 → 纠错/业务处理 → 导出`

本轮（演讲稿对齐总升级计划）锁定以下产品口径，与 `docs/presentation-alignment-plan/00-LOCKED-DECISIONS.md` 一致。任何与本节冲突的旧决策由 `docs/DECISIONS.md` 中新增 ADR 显式取代，不得由单个 Agent 私自改口径。

## 1. 研判范围：全批次，无产品层上限

1. 一个导入批次成功导入 `N` 张工单，研判目标范围就是这 `N` 张；产品层不再有 50/100/300 的截断上限。
2. 前端删除“研判数量”输入；API 删除 `max_work_orders` 与 `selection_mode` 请求字段。
3. 后端可以分块、排队、限并发、断点续跑，但目标范围不可被截断后伪装完成。
4. 资源不足时任务必须明确排队或失败，不允许截断 N 后返回“完成”。

## 2. 模型选择：任务前切换，任务中锁定

1. 用户在每次研判任务开始前选择“本地模型”或“云端模型”。
2. 任务创建时持久化 Provider Profile 快照；任务运行中不可切换。
3. 下一次任务可重新选择，不依赖修改全局环境变量。
4. 本地路径必须真实执行 LLM、Embedding、结构化输出和最小端到端研判，不能只做 ping/health。
5. 云端当前适配千问，但领域层、任务处理器和数据模型不出现厂商分支。
6. 任一模型失败都不得静默切到另一模型，也不得返回规则伪造结果。

## 3. 标准分类：完整 DB44/T 2479—2024 附录 A

1. 类型体系完整对齐附录 A：14 个一级、99 个二级、515 条三级记录。
2. 类型体系是版本化主数据，前端不再维护任何分类常量。
3. 来源已提供有效标准代码时，代码到目录节点的映射是确定性的，不调用 AI 猜名称。
4. 来源没有标准代码时，分类器只能选择标准目录中的 `classification_node_id`，不得生成自由文本类型。
5. `title_tags` 只能叫“来源标记”，不能再显示为“类型标签”。
6. 分析状态、标准分类、来源标记是三个独立维度，不可混用。
7. 原文唯一重码 `090499` 保留两条不同父路径，不得擅自改成 `090599`。

## 4. 工单、事项和页面数字

1. WorkOrder 是一张不可变的原始 12345 工单，也是高频计数单位。
2. AI 研判事项（EventInstance）是从工单中拆出的独立问题；一张工单可以有多个事项。
3. 100 张工单产生 103 个事项是合法的一对多关系，不能强压成 100。
4. 多频频次按不同 `work_order_id` 计数，不能按事项数计数。
5. 全量统计由后端按同一筛选范围聚合；当前页 20 条只属于分页信息。
6. 前端长期显示说明：“一张工单可能包含多个独立诉求，因此 AI 研判事项数可能大于工单数。”

## 5. 高频规则：三天三单，按不同工单

1. 高频事件定义为：同一事件在任意连续 3 个自然日内达到 3 张及以上不同工单。
2. 窗口使用来源系统的 `reported_at`；历史回复日期、事发日期和导入时间不能替代。
3. 满足门槛必须标记 `high_frequency`，不得显示成“低频”或“未达到”。
4. 未达到门槛使用 `not_reached`；日期证据不足使用 `insufficient_date_evidence`。
5. 产品中不建立 `low_frequency` 状态或标签。数据库、API 和前端枚举中不得出现“低频事件”。

## 6. 同事件业务语义

“同一事件”指同一现实焦点对象上的同类集中问题或兼容处理链，不等于文本相似，也不要求是同一投诉人。

正向判断至少需要：

- 焦点项目/场所/企业等现实对象相同；
- 问题类型相同或明确兼容；
- 受理时间窗口兼容；
- 不存在地点、对象、问题或处理链硬冲突。

只有“欠薪”“美的”等通用词相同不能建立同事件边。

## 7. 演讲稿验收主线

1. 美涂士五张工单必须通过通用链路自然归为一个欠薪集中事件，禁止案例特判。
2. 四种项目叫法必须归一为同一现实项目，且依据可见。
3. 世贸国风滨江欠薪不能因为同为欠薪混入。
4. 美的冰箱、美的第五工业区、美的大道项目必须保持分离，并给出对象和问题类型差异。
5. 上述案例只允许出现在 Gold Set、测试名和评测报告中，生产算法不得读取案例名称或工单号做特判。

## 8. 前端明确删除项

1. Dashboard 的“质量指标 / 质量状态灯 / 暂无 Gold Set”整个板块删除并重新排版，不留空位。
2. 新增处置记录中的“附件编号”输入、状态、校验和请求字段删除。
3. 历史附件引用可以只读保留，避免破坏既有审计。
4. 删除未接真实接口、只显示“功能开发中”的假入口。

## 9. 性能目标

1. 云端 100 条干净数据：预热后连续三次 P50 ≤ 5 分钟、单次 ≤ 7 分钟。
2. 优化顺序为：减少无价值模型调用、连接复用、批量数据访问和持久化、阶段流水化、最后才是云端有界并发。
3. 云端和本地使用不同 Execution Policy，不共享一个全局并发参数。
4. 本地模型不得通过显著增加并发 KV Cache、显存或 RAM 换速度。
5. 性能优化不能牺牲全批次范围、分类目录、同事件证据或 Gold Set 质量。

## 10. 当前四个核心页面

1. 数据导入与研判
2. 工单中心
3. 多频事件
4. 事件详情/研判

可以在同一信息架构中增加处理记录区，不要为了比赛变成复杂大屏。

## 11. 不做

- 通用知识库问答
- 自动行政认定
- 自动结案/自动派单作为比赛主流程
- 个人心理诊断/画像
- 把云端模型调用写死到业务 handler；商业供应商必须隐藏在 `LLMProvider` / `EmbeddingProvider` / `SameEventMatcher` 之后
- 在生产 prompt、Python、SQL、前端或脚本中判断案例名后固定聚五张
- 用 imported_at 冒充 reported_at
- 把 103 个事项强制压成 100
- 在数据库/API/前端保留 `low_frequency` 枚举
- 做全库 O(N²) 两两比较
- 用 Embedding 分数直接创建同事件边
