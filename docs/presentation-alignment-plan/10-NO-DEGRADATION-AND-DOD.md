# 10｜禁止降级与完成定义

## 1. 明确禁止的快捷实现

以下任何方案即使现场看起来成功，也不算完成：

- 在生产 prompt、Python、SQL、前端或脚本中判断“美涂士”后固定聚五张；
- 写死五个工单号；
- 写死三个“美的”必须分开；
- 插入预制 cluster JSON 或演示数据库快照；
- 只为这 100 条准备一份案例别名表并称为通用能力；
- 把 max count 从 300 改成更大的常数；
- 前端隐藏上限、后端仍截断；
- 失败后减少研判工单；
- local 失败静默走 cloud，或反向切换；
- 模型失败后用规则返回假“已分析”；
- 本地验证只做 ping、health 或模型列表；
- 给本地模型使用简化分类目录；
- 把附录 A 只实现成 14 个一级标签；
- 前端维护独立的两个/十几个类型常量；
- 将自由文本 `event_type` 冒充标准分类；
- 擅自把原文 `090499` 改成 `090599`；
- 为 13 条空三级名称伪造标准名称；
- 用 imported_at 冒充 reported_at；
- 把历史回复日期当当前受理时间；
- 用当前页 20 条推算全量状态；
- 将 103 个事项强制压成 100；
- 按 Event Instance 数计算三天三单；
- 满足门槛后显示“低频”或“未达到”；
- 在数据库/API/前端保留 `low_frequency` 枚举；
- 用 Embedding 分数直接创建同事件边；
- 做全库 O(N²) 两两比较；
- 取最长摘要作为聚类名称；
- 通过扩大本地并发显著增加 RAM/VRAM；
- local/cloud 继续共用一个全局并发参数；
- catch 后继续轮询并隐藏错误；
- 删除或 skip 失败测试；
- 在没有真实 Gold Set 结果时显示准确率；
- 保留质量指标空卡或仅用 CSS 隐藏；
- 保留附件编号输入但不提交；
- 用 TODO、stub、mock、静态 fixture 或测试 provider 进入生产路径；
- 把计划中的目标状态提前写成 DONE。

## 2. 产品行为完成定义

- 上传多少张成功工单，就自动研判多少张；
- 前端和产品 API 无研判条数上限字段；
- 本地/云端可在任务开始前切换，任务开始后锁定；
- 本地真实最小完整链路通过，无云端调用；
- 云端千问真实 100 条链路通过；
- 任一 provider 失败都明确可见且无 fallback；
- 所有页面数字口径清楚；
- 一张工单多事项能力保留；
- 没有质量指标板块、附件编号输入和低频标签。

## 3. 附录 A 完成定义

- 14 个一级、99 个二级、515 条三级记录全部存在；
- 唯一 `090499` 重码按完整父路径区分；
- 13 条空三级名称保真；
- 来源代码确定性映射；
- 无代码分类只能选择标准 node；
- 工单表头、筛选、详情、Dashboard 和导出使用同一 taxonomy；
- 分析状态、标准分类、来源标记完全分离。

## 4. 主案例完成定义

- 五张美涂士工单自然形成一个五工单组；
- 当前投诉中的项目没有被历史回复覆盖；
- 四种项目名称可解释归一；
- 分类为 `080508`；
- 受理时间均为 2025-03-31 且 provenance 合法；
- 世贸国风滨江欠薪不进入；
- `frequency_status=high_frequency`；
- 页面展示关联和高频依据；
- 生产路径不存在案例特判。

## 5. 反例完成定义

- 冰箱质量、工业区噪音、道路项目欠薪分别映射正确标准代码；
- 三个“美的”不合并；
- Hard Negative 实际经过判定链；
- 负向原因可追踪，不是偶然没召回。

## 6. 高频完成定义

- 使用 reported_at；
- 任意连续 3 个自然日窗口；
- 达到 3 张及以上不同 Work Order 即 high_frequency；
- 同一工单多个事项只计一单；
- 聚类/时间纠正后自动重算；
- 只有 high_frequency、not_reached、insufficient_date_evidence；
- 页面、API 和数据库无 low_frequency。

## 7. 性能完成定义

- 云端 100 条预热后三次 P50 ≤ 5 分钟、单次 ≤ 7 分钟；
- 性能报告包含各阶段 P50/P95、请求数、token、429、重试和候选量；
- 候选调用显著收敛且 Gold Set Candidate Recall=100%；
- local/cloud Execution Policy 分离；
- 本地峰值资源不超过基线 110%；
- 提速不减少工单、不跳过事项、不降低分类或同事件质量。

## 8. 架构与工程完成定义

- API 薄，领域层不依赖 FastAPI、SQLAlchemy、具体模型厂商和前端；
- 基础设施通过 typed ports/adapters；
- 无全库 O(N²)；
- 原始工单不可变；
- 模型输出、Embedding、taxonomy 和知识快照可缓存、可版本化；
- 人工纠正不可变且重跑保留；
- 数据库变更有 Alembic；
- 后台任务幂等、可恢复；
- mandatory backend/frontend/Playwright 检查全部通过；
- CURRENT_STATE、DECISIONS、ARCHITECTURE、TRAE_HANDOFF 与实现同步；
- Git 剩余文件均有明确归属。

## 9. 本轮边界

本轮不要求：

- 删除后端历史附件存储和旧审计数据；
- 在浏览器保存云端 API Key；
- 用本地模型完整跑 100 条性能验收；
- 在 Dashboard 建宣传型质量大屏；
- 修改锁定的痛点原文；
- 为任何演示案例增加生产特判。

“不要求本地完整跑 100 条”不等于本地功能可不通。本地 LLM、Embedding、分类、SameEvent 和最小完整 E2E 必须真实通过，且正式任务架构必须支持完整批次。

## 10. 状态规则

只有本文件全部完成条件有可核实测试或运行记录时，本计划才可标记 `DONE`。困难、耗时或硬件限制都不能把验收项删除或改成静态演示；未满足就保持 `PARTIAL/BLOCKED` 并写清证据。
